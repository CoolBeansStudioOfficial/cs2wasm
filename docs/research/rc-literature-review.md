# Static proofs, not run-time tricks, must close the gap

The literature backs the shape of il2wasm's design, and it also shows that the design's hardest promises have no precedent. Getting from 53–57% of count operations removed to Lobster-like levels does not need new theory. It needs four levers the earlier compiler most likely lacked: ownership signatures for every library and BCL method, speculative borrows that become owners only when something writes to what they borrow, caller-side repair of conflicting writes, and Gel's interprocedural rule that "this live range cannot free type T". On cycles, a 2025 lower bound shows that no run-time scheme frees an arbitrary cut-off mutable cycle at the cutting statement in bounded work. il2wasm's owner chains are therefore the right bet and the only one available, but no production compiler proves automatically that a back reference points to its owner, so that proof is new work. On threads, WebAssembly offers only sequentially consistent atomics, which lower to `lock xadd`. That makes static thread-escape analysis worth more on wasm than on native code. Almost every run-time technique the literature uses to cheapen shared counts (biased counting's merge queue, CPython's deferred counts, Koka's sign bit, Lean and Koka's `is-unique` reuse) breaks one of the fixed constraints. Finally, every mature RC compiler (Swift, Lean, Koka, Lobster) re-derives or re-canonicalizes ownership after inlining and devirtualization, and none settles it once. So the "one whole-program analysis" should be one monotone fixed point that includes call-graph and type resolution, followed by cheap local re-canonicalization after inlining. It should not be a single pass whose answers are frozen.

## Where a 53–57% compiler leaks its count operations

Lobster's claim that its analysis removes "around 95% of runtime reference count operations" is the benchmark the owner cares about. That figure is unqualified. The documentation names no method, gives no per-program data, and does not say whether it counts static sites or executed operations. The only evidence is "several dozens of Lobster programs" ([Lobster memory management](https://aardappel.github.io/lobster/memory_management.html)). Current master now has an `--rcstats` mode that counts executed incs and decs per site ([LOBSRC/vmdata.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/vmdata.h)), but nothing shows that the 95% was measured with it. The number is therefore a target, not a reproducible baseline. il2wasm should measure itself the way `--rcstats` does: executed operations per site, with operations done inside the runtime's own code counted separately.

What makes the figure possible is clear from the source. Lobster gives every AST node, not just every variable, an ownership kind. A mismatch between parent and child is fixed with one inc, one dec, or an anonymous temporary (`AdjustLifetime` in [LOBSRC/typecheck_base.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/typecheck_base.h)). Most of the removals come from a few defaults. **Single-assignment locals initialized from a variable, field or element borrow "speculatively"** and flip to owners (`FlipSpeculative`, which adds one inc on the initializer) only if something writes to what they borrow ([LOBSRC/idents.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/idents.h), [LOBSRC/typecheck_locations.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/typecheck_locations.h)). Parameters own only if they are reassigned (`ParamOwns`). **Builtins borrow all their arguments, and only marked sinks such as `push` own** ([LOBSRC/natreg.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/natreg.h)). When a write conflicts with a borrowed parameter, `KeepArgAlive` gives the caller's argument its own reference. The source comment calls this "Cheaper than making the parameter own, which every call would pay for". Functions of 25 nodes or fewer are specialized per argument ownership. Big functions and all functions in a dynamic dispatch get one borrowing signature ([LOBSRC/typecheck_calls.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/typecheck_calls.h)). The notes infer, reasonably but without a measurement, that a compiler stuck at 53–57% is most likely missing the borrowing signatures for library calls and getters, plus the speculative borrow with flip-on-write. Without those, any local that might be invalidated is conservatively made an owner. For .NET this means every BCL method needs an ownership signature: which parameters it stores, and whether it returns a borrow (getters, indexers, `List<T>[i]`).

Lobster's correctness argument does not carry over whole. Its borrows are invalidated only by writes to a path that is a prefix of the borrowed path, with aliases expanded. Any expression that is not a path "gets a generic borrow, which disables lock checks, so is unsafe" (comment in `PushBorrow`, [LOBSRC/typecheck_base.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/typecheck_base.h)). The checker's own "FIXME: this should really just not be possible, but hard to guarantee" admits the same gap. Since .NET behaviour must not differ, il2wasm has to give such borrows an owned reference rather than accept the hole. Lobster also has no shared mutable heap across threads, no finalizers, no weak references (rejected for their overhead, [Lobster issue #151](https://github.com/aardappel/lobster/issues/151)), and it leaks cycles, reporting them at exit. One part of its code generation conflicts with il2wasm's rule: values only borrowed by their consumer are kept in a per-function "keep" slot until the function returns or the loop comes round again (`EmitKeep`, [LOBSRC/codegen_refcount.h](https://raw.githubusercontent.com/aardappel/lobster/master/dev/src/lobster/codegen_refcount.h)). That frees later than the statement that makes the value unreachable, so il2wasm must not copy it.

**Gel is the lever Lobster lacks, and it targets exactly the C# setting.** Dingle and Bacon's Gel is a C# subset with one owning pointer per object and run-time counts for non-owning pointers. Its elimination rule is type-based and interprocedural: if a block of code never mutates an owning pointer whose type is T, a supertype of T or a subtype of T, then no non-owning local of type T whose lifetime lies inside that block needs a count. The analysis builds a call graph and computes, for each method, the set of owning field types it may store. It eliminated **89–100% of executed increments**, for example 868.2M to 93.4M on sort, 225.7M to 13.0M on the 73,000-line self-compile, and **binarytrees to zero**. Speed-ups were 10–35% in the body and 20–40% in the abstract; the paper's two ranges disagree ([Dingle & Bacon, Ownership You Can Count On](https://web.archive.org/web/2019id_/http://researcher.watson.ibm.com/researcher/files/us-bacon/Dingle07Ownership.pdf)). This is a cheap effect summary over IL ("which reference field types can this call write?"), and it removes counts that Lobster's path rules would keep. Gel's own limits mark the transfer conditions. It is single-threaded because "its reference counting optimizations can not easily be applied in the presence of aliasing arising under multi-threading". It also makes a non-zero count at the owner's death a fatal error. In il2wasm that state must instead mean "not dead yet", so the summary must include stores by other threads to escaped objects.

The other prior art points the same way. Joisha's Bartok work is the nearest precedent: nondeferred RC for real C# with interior pointers and exceptions. His "overlooking roots" (a reference whose lifetime covers another's makes the other's counts redundant) reportedly brought nondeferred RC to **within 4% of deferred RC on nearly all programs and within 23% in the worst case**. That figure comes from an abstract seen via an index summary, so it is lower confidence ([ISMM 2007 bibtex](https://bibtex.github.io/ISMM-2007-Joisha.html); [sciweavers abstract](https://sciweavers.org/node/96777)). Joisha also found that a callee-retains template hides subsumption across calls, and that moving decrements later in a block buys dead-code elimination "at the expense of holding onto garbage longer". il2wasm forbids that trade ([MSR TR-2007-104](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2007-104.pdf)). CPython 3.14's `LOAD_FAST_BORROW`, which pushes an uncounted reference when the frame's reference outlives it, covers **about 97% of LOAD_FAST instructions** according to its author's pystats ([CPython PR #130708](https://github.com/python/cpython/pull/130708)). Nim's cursor inference turns `dest = src` into an uncounted alias when neither side is mutated afterwards ([Nim destructors](https://nim-lang.org/docs/destructors.html)). Taken together, these show that local and parameter traffic yields to intraprocedural liveness of the owner. The hard residue is heap fields and containers.

The Java RC data suggests how large that residue is, though it measures object age and maximum count, not syntactic site. In Shahriyar's measurements, **71% of increments and decrements hit newly allocated objects**, and **49% hit objects whose maximum count is 1 or 2**. Those are the objects a single-owner analysis should own outright, with zero count operations. Meanwhile **0.65% of objects overflow a 3-bit count yet attract about 23% of all operations**, and 17% of increments go to objects with counts above 63 ([Shahriyar thesis 2015](https://openresearch-repository.anu.edu.au/bitstream/1885/99879/1/Thesis%20Shahriyar%202015.pdf)). That popular-object share, shared containers and globals in practice, is the likely floor of any static scheme. Coalescing's 64%/90% and born-dead's 80–90% removals, by contrast, are dynamic and rest on deferral, so they do not transfer. Their static analogues are cancelling an inc against a dec on the same field within a block, and the fact that a fresh object has one owner until it escapes.

## SSA ownership transfers to the CLR, with two added proofs

Swift's Ownership SSA is the representation the design should copy. Every non-trivial value is Owned (consumed exactly once on every path) or Guaranteed (a borrow scope nested inside a live base). `copy_value` and `destroy_value` are the only count operations, and "ARC effects apply only to the specific value", so RC optimization becomes local def-use reasoning instead of alias reasoning. Pairing is a verifier invariant. Forwarding instructions pass ownership through casts and projections without counts, interior-pointer projections require a guaranteed base, and dead-end blocks need no lifetime end ([Swift Ownership.md](https://raw.githubusercontent.com/swiftlang/swift/main/docs/SIL/Ownership.md)). That last rule matters for il2wasm's error paths: a path ending in an unhandled-exception trap needs no releases, but a path that throws to a handler does. Swift's biggest single gain came from switching the default parameter convention to +0 (guaranteed), with +1 kept only for setters and initializers that store. Erik Eckstein's preliminary 2018 data showed better average benchmark performance with "some regressions" and code size "up to 5%" better ([Swift Forums proposal](https://forums.swift.org/t/proposal-to-change-the-default-ownership-for-passing-parameters/10261)). Joisha's template finding agrees. The ObjC ARC optimizer contributes the "KnownSafe" fact, meaning another reference provably holds the object across the region, and the return-value handshake that hands a +1 straight to the caller. It does not contribute its licence to move releases, which exists only because Clang declares locals to lack precise lifetime ([Clang ARC spec](https://clang.llvm.org/docs/AutomaticReferenceCounting.html); [LLVM ObjCARCOpts.cpp](https://llvm.org/doxygen/ObjCARCOpts_8cpp_source.html)). il2wasm can only move releases earlier, and only across code that cannot observe the free.

Swift's lexical-lifetimes episode is the most direct warning for .NET semantics. Swift 5.6 shortened lifetimes to the last use. Weak-reference unwraps then crashed, unsafe pointers dangled and deinit side effects ran early. Swift 5.7 therefore anchored deinits to scope end, still allowing them to run earlier unless a "deinit barrier" follows the last use: a weak or unowned load, a pointer access, an opaque call, a global access or a synchronization point ([Trick gist](https://gist.github.com/atrick/cc03c4d07fb0a7bee92c223ae5e5695b); [Swift Forums](https://forums.swift.org/t/what-is-the-current-status-of-lexical-lifetimes/76587/2)). il2wasm's rule is stricter in one direction and looser in another. Frees may not be delayed, which Swift allows up to scope end. But freeing at unreachability is itself an allowed .NET behaviour, because the JIT may collect after last use and `GC.KeepAlive` exists to stop it. The barrier list is still useful, inverted: these are the points where il2wasm's idea of "unreachable" must agree with what the program can observe. `WeakReference.Target` reads, `GCHandle` and `DependentHandle` reads, `Unsafe`/`fixed` pointers into an object, and `GC.KeepAlive` calls are the observers that must keep an object alive to the point where .NET would. With those modelled, freeing at the last use is not a behaviour change, because CoreCLR is entitled to do the same.

From the functional line, the pieces that transfer are the dataflow rewrites. Perceus passes ownership into callees, so in `ys = map(xs, inc)` the callee frees `xs` as it goes, and "For map, the memory usage is halved". It inlines the unique-free path at a known constructor (drop specialization), pushes dups into branches and fuses dup/drop pairs, after which "almost all reference count operations in the fast path are gone" ([Perceus TR](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)). Under il2wasm's static ownership the "unique" branch is known at compile time, so drop specialization becomes a direct free plus release of the children. Lean's borrow inference is a monotone fixed point per strongly connected component of the call graph. Every parameter starts borrowed and is marked owned if it reaches reset/reuse, is passed to an owned parameter or a partial application, or would break a tail call. It ends in at most as many rounds as there are parameters ([arXiv 1908.05647](https://arxiv.org/abs/1908.05647)). The 2026 LCNF version separates forced "own reasons" (tail calls including join points, reset-reuse) from performance reasons, and lets user annotations override only the latter ([InferBorrow.lean](https://github.com/leanprover/lean4/blob/master/src/Lean/Compiler/LCNF/InferBorrow.lean)). Its measured value was modest. Disabling borrowing gave a geometric mean of 1.27 against a base of 1.24 (about 2–3%), with 14–16% on binarytrees and deriv. The per-benchmark pairs were read from a linearized table, so they are lower confidence. Disabling reuse cost much more, 1.74 against 1.24 ([arXiv 1908.05647](https://arxiv.org/abs/1908.05647)). The lesson transfers with care. In Lean, nothing can overwrite the caller's reference while a callee borrows it. In C#, a borrowed `p` read from `o.f` dies if the callee or another thread does `o.f = null`. So **every borrow from a heap path needs two side conditions**: no write to that path during the borrow (Gel's mod summary, Lobster's path check) and no other thread able to write it (the thread-escape fact).

The "nothing freed later" rule creates one tension the literature names and il2wasm has not resolved. Perceus's FL-reuse paper shows that borrowing "can increase the memory usage of a program by an arbitrary amount and it is generally not frame-limited". When a caller passes its last use of `x` to a borrowing callee, `x` becomes unreachable partway through the callee but is freed only when the call returns ([FL-reuse TR](https://www.microsoft.com/en-us/research/uploads/prod/2021/11/flreuse-tr.pdf)). Koka therefore has no automatic borrow inference. Lobster's "parameters borrow by default" has the same effect. Whether this breaks il2wasm's rule depends on whether "the statement that makes it unreachable" is read at the caller's call statement or inside the callee. Under the strict reading, last-use call sites must pass ownership. That means the callee needs an owning entry, through Lobster-style ownership specialization (code size) or an owned-convention parameter (count operations at non-last-use sites). Under the loose reading, borrowing at last use is fine. The owner should settle this definition before buildout, because it decides the calling convention.

## Owner chains are the only feasible answer for cycles

Sotoudeh's 2025 result is the key validation. Any correct reachability-based collector that implements a realistic mutator-observer interface has a pathological program: formally t_AR(n)·d(n) = Ω~(log^{3/2} n), so a delay of O(1) forces superlogarithmic pauses, and under the OMV conjecture the bound becomes Ω(n). The paper's own upper-bound collector keeps a spanning forest in Euler-tour trees, gets delay 1 and O(log n) pauses on acyclic heaps, and is declared not competitive ([Sotoudeh, arXiv 2504.11654v2](https://arxiv.org/html/2504.11654v2); [ACM DL 10.1145/3720430](https://dl.acm.org/doi/10.1145/3720430)). Read against il2wasm's constraints, this means **"free at the cutting statement with bounded work" cannot hold for arbitrary mutable graphs under any run-time scheme**. It can hold only where compile-time structure supplies the spanning tree. An owner chain is that tree, maintained with O(1) work per store because type and store-site proofs fix the tree edges. The same paper shows that Brownbridge's strong/weak split, which il2wasm's uncounted back references resemble, claimed more than it delivered. Salkild showed it could free reachable memory, and Pepels et al.'s scheme takes asymptotically longer than plain RC on acyclic heaps. Uncounted edges therefore need a checked proof, not an argument.

Gel shows what an owner chain buys. When an owner is destroyed, Gel destroys the object's fields first (recursively for owning fields, decrementing for non-owning ones) and only then checks the object's own non-owning count. As a result, **"Gel can automatically destroy any data structure in which every non-owning pointer from an object o points to an object which is an ancestor of o in the ownership tree"**, including doubly linked lists and parent pointers, with no walk beyond the free itself ([Dingle & Bacon](https://web.archive.org/web/2019id_/http://researcher.watson.ibm.com/researcher/files/us-bacon/Dingle07Ownership.pdf)). Gel checks this with a run-time count. A static proof that a field always holds an ancestor would remove both the count and the check. Gay and Aiken's `parentptr` and `sameregion` annotations are exactly such a statically checked "this pointer goes up the tree, skip the count". They cut RC overhead from a worst case of 27% to 11%; that figure comes from the abstract via search, so it is lower confidence ([UCB/CSD-00-1115](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2000/5340.html)). Verona/Reggio's regions, each entered through one owned bridge object, are reportedly the region-level form of the same idea. The paper text was not extracted, so this is unverified ([MSR PDF](https://microsoft.com/en-us/research/uploads/prod/2023/10/oopslab23main-p377.pdf)). Ownership domains, which declare permitted cross-domain links, model il2wasm's accepted "outside references into a group" better than strict owners-as-dominators. Those sources were not re-fetched and are lower confidence.

What has no precedent is inferring these facts from unannotated code. Nim asks the programmer for `{.acyclic.}`, which the ORC announcement says "can be crucial" for performance ([Nim ORC](https://nim-lang.org/blog/2020/12/08/introducing-orc.html)). Swift asks for `weak`/`unowned`. Gel and Gay-Aiken ask for annotations. il2wasm must infer from IL what Nim leaves to the programmer, so its back-reference proof is a novel requirement. The notes spell out what a sound parent-pointer proof must show: every store to `x.Parent` stores the object whose child field holds `x`; that child field is the only owning path to `x`; and no read of `Parent` happens after the parent is freed. These are shape-analysis properties, not type properties. The academic shape-analysis literature (TVLA, separation logic) was not surveyed, and that is a real gap in this review. Two further proofs follow from Gel's destruction order. Group destruction is recursive, and Gel notes it "may use a large amount of stack space", which matters on wasm's bounded stack. Destruction should use an explicit worklist, which still runs inside the cutting statement and so defers nothing. And Elsman's 2023 fix to MLKit, where pointers that regions allow to dangle became unsafe once a tracer followed them ([Elsman PLDI 2023](https://dl.acm.org/doi/10.1145/3591229)), is the warning that anything which follows an uncounted back reference must never see a freed owner. That includes finalizers, weak-reference reads, reflection and debuggers.

The awkward finding is the fallback. Where a proof fails, the literature offers two choices and no third. One is a per-group count that keeps the whole group alive while any outside reference exists, as in Parkinson et al.'s per-SCC counts for frozen graphs ([MSR ISMM 2024](https://www.microsoft.com/en-us/research/publication/reference-counting-deeply-immutable-data-structures-with-cycles-an-intellectual-abstract/)). That frees a cut sub-cycle later than the cutting statement, which conflicts with the constraint. The other is unbounded work, a walk, which also conflicts. Every region system shows the same pattern: MLKit adds a copying GC, Gay and Aiken add per-region counts, Cherem and Rugina add individual frees, because regions cannot reclaim a cut part of a live region ([Hallenberg, Elsman, Tofte, PLDI 2002](https://www.researchgate.net/publication/2525968_Combining_Region_Inference_and_Garbage_Collection)). The design therefore has to make the residue as rare as possible with stronger proofs. It also needs an explicit owner decision for programs whose cyclic structure no proof covers. "Any C#" and "freed at the statement, no walk" cannot both hold for those programs. Parkinson's per-SCC idea does fit one case cleanly: graphs that are frozen and never written again (reachable only through `static readonly` and init-only fields after construction). A single count per frozen SCC is exact for those, and their SCCs never split.

## Finalizers and weak references force a fixed destruction order

.NET fixes ordering rules that a prompt-free runtime must reproduce exactly. A short `Weak` handle is "zeroed before the finalizer runs, so even if the finalizer resurrects the object, the `Weak` reference is still zeroed". `WeakTrackResurrection` handles survive resurrection ([GCHandleType](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.gchandletype)). A `DependentHandle` is "conceptually equivalent to having a weak reference to a given target object instance A, with that object having a field ... to a dependent object instance B" ([DependentHandle](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.dependenthandle)). A `ConditionalWeakTable` value never keeps its key alive, "even if it can be reached directly from a value stored in the table" ([ConditionalWeakTable](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.conditionalweaktable-2)). CPython's PEP 442 is the nearest implementation of comparable semantics under RC. For a cyclic isolate it clears weakrefs first, runs every finalizer, traverses again and aborts if anything was resurrected, and only then breaks references. A finalized bit guarantees each finalizer runs exactly once ([PEP 442](https://peps.python.org/pep-0442/)).

That ordering maps directly onto group death in il2wasm, with one substitution. Clearing the short weak handles of every object in the dying group before any finalizer runs costs work proportional to the group's handles, which stays within "work bounded by what changed". Every finalizer in the group must run before any memory is released, because a child's finalizer may read an uncounted `Parent`. PEP 442's step 3 re-check is a walk, so il2wasm must replace it with counting. A finalizer that resurrects does so through a counted store, so if the group's outside count is non-zero after its finalizers have run, the free is aborted. That makes finalizable objects effectively group roots whose death is decided by counts. CWT and DependentHandle entries become group edges from key to value, and references from the value back to the key do not count as outside references. That is the owner-back-reference problem again, which is a reason to build ephemerons on the same group machinery rather than as a special case. None of the sources implements .NET's full finalizer, short/long weak and ephemeron semantics on prompt RC without a tracer, so this part of the design has no precedent either.

Two points in the notes conflict with the fixed constraints and should not be adopted. First, the threads note suggests queuing finalizers to a single finalizer thread in drain order to keep them deterministic. That moves work to later, which the constraints forbid. Second, running finalizers inline at the cutting store is not observably the same as CoreCLR in every case, and the notes flag this without resolving it. .NET runs finalizers on a dedicated thread. Inline execution runs them on the mutator thread, possibly while it holds a monitor. Because `Monitor` is reentrant, a finalizer that takes a lock the mutator holds succeeds inline where CoreCLR would block, and `Thread.CurrentThread` inside the finalizer differs. .NET leaves finalizer timing unspecified, so most programs cannot tell the difference, but a strict reading of "identical to .NET, including every error path" makes this an owner decision. The candidate answers are to accept inline execution as one of .NET's permitted schedules, or to restrict it where the analysis sees the finalizer touch locks or thread identity. Finalizer order within a group will be deterministic, for example post-order down the owner chain. .NET leaves that order unspecified, so tests must accept any order.

## Wasm atomics make static thread escape worth more than on native code

The cost model on WebAssembly is harsher than the native literature assumes. All wasm atomics are sequentially consistent, misaligned atomics trap, and `wait` traps on unshared memory and on the browser main thread ([WebAssembly threads Overview](https://github.com/WebAssembly/threads/blob/main/proposals/threads/Overview.md)). V8's Liftoff lowers `i32.atomic.rmw.add` to `LOCK XADDL` on x86-64 ([v8-dev thread](https://www.mail-archive.com/v8-dev@googlegroups.com/msg162287.html)). There is no relaxed increment, which is the ordering a native `Arc` uses. In BRC's native measurement an uncontended atomic increment cost **13.84 ns against 5.77 ns plain, 2.40x** ([BRC paper](https://docs.rs/crate/biasedrc/latest/source/paper.pdf)). No wasm-specific microbenchmark was found. The shared-everything-threads proposal would add `thread_local` globals and acquire/release orderings, but it is still changing and is unimplemented in Wasmtime ([shared-everything-threads](https://github.com/WebAssembly/shared-everything-threads/blob/main/proposals/shared-everything-threads/Overview.md); [Wasmtime proposals](https://docs.wasmtime.dev/stability-wasm-proposals.html)). Whether engines lower atomics on unshared memory to plain operations is unknown, so the threads-off build should emit no atomics at all. That meets the "no slower without threads" bar by construction rather than by trusting the engine. Apple's claim that uncontended atomics are "almost as cheap as nonatomic accesses" is unmeasured in its source and does not apply to wasm on x86 ([Swift forums](https://forums.swift.org/t/swift-performance/28776/105)).

Dynamic measurements show how much data is really thread-local, and the static analyses show how much of that they recover. BRC found over 99% of objects in Swift client programs and over 93% in servers private, and about 93% and 87% of RC operations on private objects ([BRC paper](https://docs.rs/crate/biasedrc/latest/source/paper.pdf)). DaCapo has 69% thread-local objects ([Loci](http://janvitek.org/pubs/ecoop09.pdf)). VolanoMark, which is thread-per-connection, has 45–48% ([Jones and King](https://www.cs.kent.ac.uk/pubs/2005/2228/content.pdf)). Choi et al.'s escape analysis eliminated a median 51% of lock operations, with a range of 11–92%; those numbers come from secondary slides and are lower confidence ([UNICAMP slides](https://www.ic.unicamp.br/~edson/disciplinas/mo615/2011-2s/seminario/mo615-2s11-seminario-escape_analysis-slides.pdf)). Two results shape the design. Salcianu and Rinard's interthread analysis gave "little additional benefit" over intrathread escape for synchronization removal, though it was needed to prove region safety on Barnes and Water ([PPoPP 2001](https://people.csail.mit.edu/rinard/paper/ppopp01.pdf)). And Domani et al. found that partial identification does not pay: placing 50% of objects directly in the global heap made throughput worse, and about 99% accuracy on hot sites was needed for the full benefit. They also criticize static analysis because one allocation site producing 90% local objects is still classed global ([Domani et al., ISMM 2002](https://csaws.cs.technion.ac.il/~erez/Papers/TLH-ISMM-02.pdf)). For il2wasm the consequences are concrete. The analysis must be context-sensitive at hot allocation sites, cloning a site by calling context where needed. Statics are escaping only if a thread-start reachable in the whole program can reach them, not unconditionally as in Jones and King. And a program with no reachable `Thread`, `Task.Run`, `ThreadPool` or `Parallel` entry is entirely thread-local, so it runs on plain counts with no analysis cost at all.

The run-time techniques for cheapening shared counts almost all break a constraint. **Biased reference counting** keeps an owner-only plain counter and an atomic shared one. Its owner path costs a thread-ID check, 8.8% above plain. But a non-owner decrement can drive the shared counter negative, and the object is then queued for the owner to merge later. That is a deferred free, forbidden here. Its free timing also depends on which thread drops last ([BRC paper](https://docs.rs/crate/biasedrc/latest/source/paper.pdf)). CPython's free-threaded build adds deferred counting reclaimed only at GC and QSBR for freeing memory, both forbidden ([PEP 703](https://peps.python.org/pep-0703/); [Python 3.14 HOWTO](https://docs.python.org/3.14/howto/free-threading-python.html)). Koka's negative-count shared bit is a run-time "is shared" test, which the constraints rule out for deciding borrows. Its static half, where only thread start and stores into thread-shared references make an object shared, is exactly the analysis il2wasm wants. Koka's measurement of making all RC atomic ("from 5% (rbtree) up to 59% (nqueens)") is the cost of getting this wrong ([Perceus TR](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)). Concurrent deferred RC defers decrements by construction ([PLDI '21](https://par.nsf.gov/servlets/purl/10252248)). What remains is a static split. Plain counts are emitted where the escape proof holds and plain seq_cst atomic counts where it does not, with no run-time mode test, plus a marking step at publication points, which in C# are stores into fields of possibly shared objects. Lean's rule that a multi-threaded value may reach only multi-threaded or persistent values ([arXiv 1908.05647](https://arxiv.org/pdf/1908.05647)) is the invariant that analysis must maintain statically. Lean also gives a free use for C# literals and `static readonly` data: "persistent" objects whose counts are never touched, which matches PEP 683's immortals without needing a GC.

C#'s task-based APIs are where escape inference is most likely to go wrong. SE-0414's review found soundness holes in captures of isolated closures, key paths and `assumeIsolated` ([SE-0414](https://github.com/apple/swift-evolution/blob/main/proposals/0414-region-based-isolation.md)). The C# equivalents are lambdas passed to `Task.Run`, `ThreadPool` or `Parallel.For` (whose display classes publish everything they capture), delegates stored in statics, `GCHandle` and `Unsafe`. `[ThreadStatic]` and `ThreadLocal<T>` are thread-local by construction and should not count as escapes. Salcianu-Rinard's fork/join modelling could recapture objects after `await` or `Wait()` joins, but the notes find no measurement of thread-escape precision for C# or async-heavy code at all. The same escape fact elides `lock(obj)` on thread-local objects. The notes infer that counts on objects reachable only under a held monitor could be updated plainly, ordered by the lock's acquire and release. That idea is untested in the literature. On determinism, deterministic multithreading costs 7–20% (Kendo, PARROT, DetLock; secondary summaries) and up to 8x (CoreDet) ([DThreads SOSP 2011](https://people.cs.umass.edu/~emery/pubs/dthreads-sosp11.pdf); [PARROT](https://www.cs.columbia.edu/~junfeng/papers/parrot-sosp13.pdf)). That would break the N-times-faster bar. Since .NET does not promise deterministic interleaving, il2wasm needs only to add no nondeterminism of its own: no address-derived hash codes, and no free order that depends on anything but program order within a thread.

## Ownership must be solved inside the same fixed point as reachability and dispatch

Every mature RC compiler interleaves ownership with inlining and specialization, and none settles it once. Swift runs the specializer, then the devirtualizer, then ARC and copy cleanups, then the inliner, then the cleanups again, in every round, because inlining exposes caller/callee copy-destroy pairs that cancel ([PassPipeline.cpp](https://raw.githubusercontent.com/swiftlang/swift/main/lib/SILOptimizer/PassManager/PassPipeline.cpp)). Lean and Koka insert RC after the functional optimizations, then fuse and specialize. Lobster interleaves ownership with type checking in call-graph order. The .NET JIT's escape analysis gained almost entirely from inlining and guarded devirtualization: .NET 10's delegate, enumerator and span cases ran 3x to 11x faster on microbenchmarks ([Performance Improvements in .NET 10](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-10)). Graal's Partial Escape Analysis works on the same SSA IR as inlining, GVN and constant folding, and pushes materialization into the branches where an object actually escapes. It cut allocated memory by up to 58.5% and raised performance by up to 33% (ScalaDaCapo factorie) ([Stadler et al., CGO 2014](https://ssw.jku.at/Research/Papers/Stadler14/Stadler2014-CGO-PEA.pdf)). PEA's states give il2wasm's ownership lattice its lower end: Virtual below FrameOwned below SingleOwner below Shared. A virtual or frame-owned object needs no count operations and possibly no count field in its header. One .NET rule should not be copied: "Objects with finalizers can't be stack-allocated since they always escape to the finalizer queue" ([object-stack-allocation.md](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/jit/object-stack-allocation.md)). In il2wasm a frame-owned finalizable object can have its finalizer run at scope end under the same rules as any other prompt finalization.

Virtual dispatch is where these interactions pay most. Lobster gives "all functions in a dynamic dispatch" one borrowing signature, and Lean wraps partially applied borrowing functions in owned wrappers ([Lobster](https://aardappel.github.io/lobster/memory_management.html); [arXiv 1908.05647](https://arxiv.org/pdf/1908.05647)). With closed-world devirtualization (ILC's scanner, Native Image saturation) the dispatch group shrinks to the overrides actually reachable. If the group signature is the most-owned demand over those reachable overrides, an override that becomes unreachable can relax the group from owned to borrowed. The notes found no paper that combines borrow inference with points-to dispatch resolution in one fixed point, so this is open territory. It is monotone if ownership demand only grows as implementations are added. Guarded devirtualization suggests a fast path specialized to borrowed arguments for the dominant receiver.

Scalability sets the limits. Combining analyses into one fixed point beats iterating separate passes ([Lerner, Grove, Chambers, POPL 2002](https://bibtex.github.io/POPL-2002-LernerGC.html); abstract only). At whole-program scale, though, production systems survive by capping precision. Native Image's saturation caps points-to sets at a threshold (about 16 gives most of the precision). At 300k methods it took the analysis from more than 9 minutes to 100 s, with linear growth ([Wimmer et al., PLDI 2024](https://www.fit.vut.cz/research/publication-file/c189291/303462/3656417.pdf)). SkipFlow's branch predicates cut reachable methods by about 9% while reducing analysis time by 1.6% ([arXiv 2501.19150](https://arxiv.org/pdf/2501.19150)). ASAP, fully precise static deallocation with no RC, had Shape and Access analyses that "appear exponential" even on generated toy programs, in a section titled "too precise for their own good" ([ASAP TR](https://www.cl.cam.ac.uk/techreports/UCAM-CL-TR-908.pdf)). Given the owner's 18–20 minute build cost against NativeAOT-LLVM's 80 s, Lobster's "pick one owner, insert an inc when unsure" plus type-based saturation is the scalable point. Per-path heap shape is not. Specialization also costs size. Lobster's 25-node cap bounds growth, and Lean's reset/reuse port gained "~15% decrease in binary size" from better exponential-code prevention ([Lean v4.30.0](https://lean-lang.org/doc/reference/4.30.0/releases/v4.30.0/)). The size goal therefore argues for specializing only where measured count traffic justifies it. Compiler determinism follows from monotonicity: a monotone fixed point has a unique least solution whatever the worklist order. Saturation, however, must be decided on final set sizes rather than arrival order, and emission order must be a sort over stable keys.

Reuse needs a CLR-specific form. Koka and Lean reuse a dead cell for a new value of the same size after a run-time uniqueness check, which is forbidden here. Lean's algorithm "can lead to an arbitrary increase in peak memory usage", and Koka's holds memory across recursive calls ([FL-reuse TR](https://www.microsoft.com/en-us/research/uploads/prod/2021/11/flreuse-tr.pdf)), which would free later than unreachability. CLR objects also have identity, finalizers and weak references. Two forms survive. One is an allocator fast path: a final free followed by a same-size-class allocation, with no call or observable event between them, hands the block across directly. The other is in-place destructive update of a statically unique, dead, non-escaping object of known type, for example an immutable-collection builder or a record `with` expression. Roc's experience is a caution about expected gains. Its whole-program uniqueness analysis Morphic gave no measurable gains outside a synthetic hot `List.set` loop (68.6 ms against 21.9 ms), was run in a "trivial" mode after a loop bug, and in January 2025 its core developers favoured removing it ([Roc Zulip](https://roc-lang.github.io/zulip-export/stream/395097-compiler-development/topic/remove.20morphic.3F.html)). Roc compared a static proof with a cheap run-time check. il2wasm has no run-time check to fall back on, so the relevant measure is what fraction of reuse sites the static proof covers, and that should be measured before reuse is built.

## Ranked recommendations for the design

1. **Give every BCL and runtime method an ownership signature, and borrow from library calls by default.** Mark which parameters a method stores, whether it returns a borrow (getters, indexers, enumerators' `Current`), and which reference field types it may write. This is Lobster's builtin rule plus Gel's mutation summary. It is the most likely cause of the 53–57% plateau and needs no new theory. Compute it from IL in the same fixed point, not by hand.
2. **Adopt OSSA-style Owned/Guaranteed values with a pairing verifier, a +0 default convention, and +1 only for storing parameters.** Repair conflicting writes at the caller (`KeepArgAlive`), not by making callees own. Run a checked build that traps on over-release, since the Brownbridge history shows that uncounted-edge schemes fail quietly.
3. **Implement speculative borrows with flip-on-write, conditioned on two proofs:** no write to the borrowed heap path during the borrow (Gel/Lobster path check, interprocedural) and no other thread able to write it (thread escape). Non-path borrows get an owned reference; Lobster's "generic borrow" hole is not acceptable.
4. **Settle the granularity of "the statement that makes it unreachable" for last-use arguments before fixing the calling convention.** Under the strict reading, last-use call sites must pass ownership, which needs owned-entry variants for small hot functions (Lobster's 25-node cap is a reasonable starting bound, tuned for size) and an owned convention elsewhere. Do not adopt Lobster's `EmitKeep` slots, Nim's scope-end destruction or Joisha's relaxed decrement placement.
5. **Make the owner-chain proof the core of cycle handling, and treat its failure cases as an owner decision.** Prove ancestor back references using the three shape conditions (store-site, sole owning path, no read after the owner's free). Destroy children-first with an explicit worklist inside the cutting statement. Sotoudeh's bound means no run-time scheme can fill the gap without a walk or late frees, so measure how much of real code (the Roslyn self-host, the Godot game) the proof covers, and bring the residue to the owner rather than quietly adding a per-group count.
6. **Build finalization as PEP 442's order with counting in place of traversal.** Clear the whole group's short weak handles, run every finalizer in the group, abort the free if the outside count became non-zero, then release memory. Keep a finalized bit, two handle kinds, and model CWT and DependentHandle entries as key-to-value group edges. Get an explicit ruling on inline finalizers versus CoreCLR's finalizer thread (reentrant monitors, `Thread.CurrentThread`). Do not queue finalizers.
7. **Split counts statically into plain and seq_cst atomic, with no run-time mode bit.** Treat "no thread entry reachable" as all-local. Treat statics as escaping only when a reachable thread entry can reach them. Clone hot allocation sites by context, since Domani's data says near-exact classification is required. Model `Task.Run` and `Parallel` closures as publication points and `[ThreadStatic]` as local. Emit no atomics in the threads-off build. Share the escape fact with `lock` elision. Reject BRC queues, deferred counts and sign bits.
8. **Run one monotone, saturating whole-program fixed point over reachability, receiver types, constants, ownership, cycle groups and thread escape. Afterwards re-canonicalize ownership locally after each inlining step, Swift-style, rather than re-solving globally.** Compute dispatch-group signatures over reachable overrides only. Use PEA's Virtual and FrameOwned states as the lattice bottom, including finalizable objects. Decide saturation on final sizes and sort emission by stable keys for byte-identical output. Keep shape precision type-based (ASAP's exponential blow-up is the cautionary bound) and budget the analysis against the existing 18–20 minute build.
9. **Treat frozen data as persistent.** Literals and `static readonly` graphs that are never written after initialization get no counting at all, or one count per SCC (Parkinson), which also removes a class of cycles from the group machinery.
10. **Defer reuse until it is measured, and build only the CLR-safe forms.** These are same-size-class free-to-allocate handoff with no intervening call, and in-place update of statically unique dead objects. Morphic's experience suggests the payoff is narrow. Never hold a reuse token across a call.
11. **Instrument like `--rcstats` from day one.** Count executed incs and decs per site, separately for runtime code, and break down the remainder by category (fields, containers, parameters, returns, popular objects). No study in the literature gives this breakdown for an OO language, and the 95% target cannot be judged without it.

## Conclusion

The review changes the framing of the problem more than it adds techniques. The count-elimination side is a solved engineering problem: Gel already got 89–100% on a C# subset in 2007, and the levers are known. The open problems are where ownership meets the other constraints. Proving back references point to owners from unannotated IL has no production precedent. Freeing cut cycles promptly without a walk is provably impossible beyond what static structure covers. .NET's finalizer, weak-handle and ephemeron rules have never been built on prompt RC without a tracer. And thread-escape precision for task-based C# has never been measured. These four gaps, not the count percentage, decide whether the design can keep every constraint at once, and each one depends on the same whole-program facts about heap shape and dispatch.

The practical upshot is that the analysis to build first is not the ownership pass itself but its inputs: per-method store and mutation summaries, closed-world dispatch resolution and context-sensitive allocation sites. Those feed borrows, owner chains, finalizer roots and thread escape alike. Two definitional rulings should come from the owner before code: what "the statement that makes it unreachable" means at a last-use call, and whether inline finalizers count as .NET-identical. Both decide calling conventions and runtime structure, and both are cheap to settle now and expensive to change after buildout.
